# Проверка результата

Проверку делает не тот, кто делал работу. Твоя задача — организовать её, а не
провести самому.

## Порядок, который нельзя менять

**1. Сначала кодом.** Всё, что можно посчитать, считается до того, как к работе
подключится модель.

```
python tools/check_links.py <артефакт>
```

Если проверки кодом дали `fail` — дальше не иди. Возвращай работу автору: модели
незачем рассуждать о тексте, в котором мёртвые ссылки и числа не сходятся.

**2. Убедись, что рубрика есть.** Нет рубрики — не запускай проверку. «Проверь,
всё ли хорошо» даёт разный результат при каждом запуске и не ловит ничего
конкретного. Если рубрики нет, собери её из шаблона `references/rubric.md` под
эту задачу и покажи человеку.

**3. Запусти проверяющего с чистым контекстом.** Субагентом `reviewer`, передав
ему **только** два файла: артефакт и рубрику.

Не пересказывай ему, что делал первый агент, какие места считаешь слабыми и на
что обратить внимание. Ровно это и есть смысл свежего контекста: он не должен
унаследовать чужую логику вместе со слепыми зонами.

**4. Сохрани вердикт файлом.** Рядом с артефактом: `<имя>.review.md`. Не в чат.
Артефакт проверки должен пережить сессию — иначе через неделю не восстановить,
что проверяли и что решили.

## Что сделать с вердиктом

| Вердикт | Действие |
|---|---|
| `PASS` по всем пунктам | работа готова, скажи об этом |
| Есть `FAIL` | верни автору с конкретными пунктами; не правь молча сам |
| Есть «нужно решение человека» | вынеси человеку, сформулировав вопрос и варианты |

Последнее — не недоработка проверки, а её главный результат. Не превращай такие
пункты в `PASS`, чтобы отчёт выглядел чище.

## Когда проверка не нужна

Не запускай её на всём подряд. Она стоит денег и времени и нужна там, где ошибка
дорогая: факты о компании, цифры для клиента, тексты на публикацию. Для черновика,
который человек и так прочтёт глазами, достаточно проверок кодом.

Пиши на русском; идентификаторы, ссылки и код — как есть.
