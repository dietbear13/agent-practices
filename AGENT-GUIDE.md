# Руководство для агента

Сравни шесть практик с рабочим пространством пользователя и предложи минимальные
изменения, которые решают обнаруженные проблемы. Используй существующие правила
и структуру проекта. Образцы здесь предназначены для адаптации.

Порядок из доклада: задача → источники и доступы → файлы проекта → план и вопросы.
Практики ниже раскрывают этот порядок, включая хранение материалов,
ключей, эталоны и проверку. Не своди разбор к наличию шести файлов.

Для чтения достаточно ссылки. Если относительные ссылки недоступны в твоём
инструменте, файлы можно читать по адресу
`https://raw.githubusercontent.com/dietbear13/agent-practices/main/<путь>`.
Если доступа нет, сообщи, какие материалы не удалось прочитать; не выдумывай их
содержание. Установка инструментов и изменение конфигурации агента не требуются.

## 1. Прочитай доступные файлы проекта

Определи границы рабочего пространства из запроса и текущей папки. Выясни,
один сайт здесь или несколько и какие документы у них общие. Прочитай местные правила,
описания задач, нужные скиллы, приоритеты, досье и `.gitignore`, если они есть.
Посмотри, где хранятся разовые результаты и общие инструменты. Если доступен Git,
используй список отслеживаемых файлов и статус, чтобы проверить границы хранения.

Возьми одну реальную задачу как пример. Проследи, где её инструкция, входные данные,
источники, результат и критерии приёмки. Для регулярной отличай многоразовый код
от результатов отдельных запусков; для разовой проверь, собраны ли её материалы
в одном месте. Если Git не используется, всё равно проверь организацию папок.
Посмотри, есть ли эталоны в `references/` или другом принятом месте, как ведутся
план и доступы, что происходит при сбое получения свежих данных.
Для повторяющихся API-запросов проверь, какие параметры закреплены инструментом,
а какие выбирает LLM. Готовый MCP может быть достаточен; свой нужен при конкретном
пробеле в возможностях или ограничениях, а не по умолчанию. Проверь, помогли бы
примеры «как надо / как не надо» объяснить требования. Отсутствие few-shot само
по себе не считай недостатком: он полезен, но не обязателен в каждой задаче.
Проверь, есть ли удобная общая папка входящих материалов (`temp/` или существующий
аналог), куда человек кладёт документы и скриншоты без сортировки. Правила должны
объяснять, как агент выбирает материалы для задачи, сохраняет нужные исходники
и отделяет их от остальных файлов. Не требуй от человека заранее раскладывать
входящие по сайтам. Не считай содержимое `temp/` автоматически ненужным или
относящимся ко всем сайтам.

Проверь хранение строковых ключей и JSON-файлов по
[практике хранения ключей](practices/secrets.md): сначала пути, права,
игнорирование и отслеживание Git, затем доступная локальная проверка содержимого
без вывода значений. Учитывай скрытые и игнорируемые файлы в границах пространства.
Не обследуй глобальные настройки по умолчанию. Не открывай файлы с секретами
в контекст ради этого разбора и не цитируй случайно встретившиеся значения.
Не выводи строки с ключами в доказательствах и diff. Не принимай
отсутствие доступа за отсутствие файла или практики; укажи непроверенную область.

Если данных недостаточно, обозначь неизвестное. Спрашивай только о том, что
существенно влияет на предложения и не выясняется из доступных материалов.
Продолжай ту часть разбора, для которой данных хватает.

## 2. Определи применимость шести практик

Прочитай практики и сопоставь их признаки с задачами проекта:

| Практика | Образцы |
|---|---|
| [Регулярные и разовые задачи](practices/tasks.md) | [Описание скилла](examples/skill.md) |
| [Границы Git](practices/git-boundaries.md) | [Фрагмент gitignore](examples/gitignore.txt) |
| [Хранение ключей и безопасная проверка](practices/secrets.md) | [Строковые ключи и JSON-файлы](examples/secrets.md), [фрагмент gitignore](examples/gitignore.txt) |
| [Один скилл — одно действие](practices/skill-design.md) | [Описание скилла](examples/skill.md) |
| [Приоритеты и досье](practices/priorities-and-dossier.md) | [Приоритеты](examples/priorities.md), [досье](examples/dossier.md) |
| [Проверка результата](practices/verification.md) | [Промпт проверки](examples/review-prompt.md) |

Для каждой укажи: «есть», «частично», «нужна», «не нужна сейчас» или «недостаточно
данных». Отсутствие отдельного файла само по себе не проблема: нужные сведения
могут уже находиться в другом месте.

В частности, проверь, что агент направляется к общим приоритетам и досье выбранного
сайта действующими правилами. Проверь согласованность текста, деревьев папок, примеров путей
и правил Git: они должны описывать одно разделение общих и относящихся к сайту
материалов. Убедись, что старые выводы не стали постоянными установками без решения пользователя,
а вопросы об источниках и методике выясняются до зависимой работы. Если задача
постоянно переделывается, сравни вводные, эталон и план, прежде чем предлагать
дополнительные инструменты или исполнителей.

## 3. Покажи находки с доказательствами

Дай короткую таблицу: практика, состояние, доказательство, последствия.
Доказательство — путь и строка, конкретный фрагмент или наблюдаемый результат
проверки. Для «не найдено» укажи область поиска. Отделяй ошибки от предположений
и того, что не удалось проверить. Не придумывай проблемы ради заполнения таблицы.
Для секретов доказательство содержит только путь, номер строки при наличии
и тип проблемы без исходной строки и значения. Различай подозрительное имя,
подтверждённый секрет в неподходящем месте и возможное раскрытие в истории.

## 4. Предложи минимальные изменения

Для каждой полезной правки покажи проблему, целевой файл или место хранения,
конкретный фрагмент изменения и способ проверки. Сначала предлагай то, что
сильнее влияет на результат. Если всё подходит, так и скажи.

- В пустом проекте исходи из первой реальной задачи: можно ограничиться промптом
  и папкой для её материалов. Не создавай набор файлов заранее.
- Для одного сайта с существующими файлами дополняй действующие документы там,
  где они уже лежат. Не создавай второй комплект правил, приоритетов и досье,
  не переноси папки ради совпадения с примером.
- Для нескольких сайтов сохраняй общие экспертные приоритеты в одном месте;
  общими могут быть также методики, скиллы и инструменты. Разделяй факты, доступы
  и данные сайтов. Отсутствие файла приоритетов внутри папки сайта не считай
  недостатком, если действует общий. Проверяй область действия документов,
  а не только их расположение.

Применение зависит от запроса пользователя: если он просит разбор, верни разбор;
если уже поручил изменения, выполни их в разрешённых границах. Не требуй повторного
согласования уже разрешённых действий. Если необходимое действие выходит за эти
границы, сначала подготовь конкретное предложение.

После изменений проверь соответствие задаче, ссылки и ожидаемый состав изменений.
Сообщи, что изменено, какие проверки выполнены, какие ошибки остались и что
проверить не удалось. Отчёт файлом сохраняй только когда это нужно задаче.
