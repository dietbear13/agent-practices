# Один скилл — одно действие

Скилл — переиспользуемая инструкция с понятными входом, действием и результатом.
По названию и описанию должно быть ясно, когда её применять. Одно действие может
состоять из нескольких шагов, если они ведут к одному определённому результату.

Не объединяйте независимые задачи только потому, что они относятся к одной теме.
Справочную информацию выносите отдельно, когда она мешает читать основную
инструкцию; оставляйте ссылку и объясняйте, когда справка нужна.

## Что должно быть в инструкции

Укажите, когда вызывать скилл, какие входные данные нужны, какой инструмент
использовать, какие параметры передавать, куда сохранять результат и как его
проверять. Опишите поведение при недоступном источнике и неполных данных.
Общему скиллу передавайте выбранный сайт, его источники и каталог результата
как параметры. Приоритеты и общая методика читаются из единого места;
копия скилла для каждого сайта не нужна. Пути берутся из действующих правил
пространства, как в [примере хранения](tasks.md#рабочее-пространство-и-сайты).
Один сервис не требует отдельного скилла на каждый способ подключения: для
одного действия можно указать основной инструмент и допустимую альтернативу.

Скилл задаёт порядок действий и условия вызова. Скрипт исполняет фиксированный
алгоритм; MCP предоставляет доступ к инструментам сервиса. Ни один из этих
вариантов сам по себе не гарантирует правильность результата.

## Пример

«Проверить суммы в таблице» получает таблицу и правила расчёта, пересчитывает
итоги и возвращает расхождения. Выгрузка данных и подготовка презентации остаются
отдельными задачами. [Образец описания](../examples/skill.md) можно адаптировать
к существующему формату инструкций пользователя.

Для работы по этой практике не нужен специальный механизм загрузки скиллов:
инструкцию можно передать агенту текстом или ссылкой. Образец в `examples/`
не является автоматически подключаемым скиллом.

## Как адаптировать чужую инструкцию

Сначала сравните её с задачей: нужны ли все действия, доступны ли сервисы,
поддерживаются ли нужные фильтры и формат. Например, упоминания GA/GSC нельзя
оставлять в инструкции для проекта, где используются Метрика и Вебмастер.
Проверьте смысл замены: похожие названия показателей не делают их одинаковыми.

Забирайте только нужное, сохраняйте источник и учитывайте лицензию. Для разового
исследования подходят доступные широкие инструменты; для повторяемого сбора и
расчёта закрепляйте проверенный скрипт или узкий инструмент. Чужие непроверенные
интеграции в докладе предлагается сначала использовать только на чтение, без
доступа к рабочим системам на запись. Наличие подключения не подтверждает его
пригодность: примите инструмент на задаче с заранее известным ответом.

## Как выбрать инструменты

### Готовый MCP, свой сервер или скрипт

| Вариант | Когда достаточно / когда нужен |
|---|---|
| Готовый MCP-сервер | Есть нужные действия, параметры и доступы; формат ответа подходит. Удобен для разовой задачи и проверки идеи. Подходит и для регулярной работы, если уже обеспечивает нужные ограничения |
| Свой MCP-сервер или адаптация готового | Сценарий повторяется, LLM должна выбирать действия и переменные параметры по запросу, но правила обращения к API должны оставаться неизменными. Готовый сервер не закрепляет эти правила, не даёт нужный отчёт или возвращает слишком много ненужных данных |
| Скрипт | Последовательность действий и формат известны; нужен фиксированный расчёт, выгрузка или запуск по расписанию. Если скрипт уже решает задачу, отдельный MCP-сервер ради самого подключения не нужен |

«Готовый» не означает «любой скачанный»: проверьте конкретные API-возможности,
права, параметры, обработку ошибок и результат на небольшом известном примере.
Своя реализация нужна из-за требований задачи, а не только потому, что инструмент
написал кто-то другой. Иногда достаточно доработать готовый сервер или обернуть
проверенный скрипт узким инструментом.

### Что фиксировать в своём MCP

**Неизменяемое закрепляйте в коде или конфигурации сервера.** Например, набор
метрик, модель атрибуции, обязательный фильтр, правила пагинации, формат ответа
и соответствие сайта счётчику. Это решения принятой методики. Если параметр
не должен меняться от формулировки запроса, не оставляйте его на выбор LLM.
Значение по умолчанию, которое модель может переопределить, не фиксирует правило.

**Переменное оставляйте аргументами инструмента.** Например, выбранный сайт,
диапазон дат, раздел сайта, порог падения или число строк — если методика разрешает
их менять. LLM извлекает эти значения из запроса пользователя, сервер проверяет
тип, допустимый диапазон и совместимость. Конкретный параметр может быть постоянным
в одной задаче и переменным в другой; это определяется до реализации.

Учебный пример инструмента поиска просевших страниц, не схема конкретного API:

```text
Запрос: «Для alfa найди страницы /blog/, где трафик за октябрь упал минимум
на 20% относительно сентября. Покажи 50 страниц».

Аргументы, которые передаёт LLM:
site = alfa
period = 2026-10-01 .. 2026-10-31
comparison_period = 2026-09-01 .. 2026-09-30
path_prefix = /blog/
drop_percent = 20
limit = 50

Сервер добавляет сам:
счётчик и доступы alfa из конфигурации;
утверждённую метрику и модель атрибуции;
обязательные фильтры принятой методики;
пагинацию, проверку полноты и фиксированные колонки результата.
```

Модель не получает аргументы для произвольной замены счётчика или отключения
обязательного фильтра. Сервер собирает API-запрос из разрешённых аргументов
и фиксированных настроек; свободный словарь параметров не должен позволять
перезаписать эти настройки. Секреты хранятся предусмотренным проектом способом,
а не хардкодятся в исходнике и не передаются через LLM.

Для нескольких сайтов используется один инструмент: `site` выбирает разрешённый
набор настроек, а сервер подставляет соответствующие идентификаторы и ограничения.
Не зашивайте один счётчик для всех сайтов. При запросе, противоречащем методике,
инструмент сообщает ограничение; изменение методики выполняется явно в коде
или конфигурации, а не обходится свободным API-параметром.

При приёмке проверьте: разные даты меняют период, выбор beta использует настройки
beta, обязательные фильтры сохраняются, неподдерживаемые переопределения отклоняются,
неполные данные не выдаются за полный результат. Примеры вызовов и ожидаемых ответов
можно включить в [few-shot](tasks.md#few-shot-инструкция-и-примеры).

## Как соединять действия

Обычно несколько небольших шагов может выполнить один агент со скиллами.
Если этапам нужны разные инструкции и отдельные контексты, передавайте между
ними файл результата: сайт, входные данные, период, источники, ограничения и критерий
готовности. Следующий этап проверяет файл перед использованием. Такой порядок
работает и при смене сессий вручную; поддержка субагентов не обязательна.
Способ продолжения по плану описан в [практике о задачах](tasks.md).

## Когда практика нужна

- По описанию нельзя понять, что будет на выходе.
- Инструкция запускает лишние действия при узком запросе.
- Основные шаги теряются среди справок, а условия применения не определены.
- Чужая инструкция требует недоступный сервис или неподходящий отчёт.
