# Регулярные и разовые задачи

Сначала определите задачу, источники и правильный результат. Затем решайте,
что сохранить для следующих запусков. У регулярной задачи переиспользуется способ
работы, но каждый запуск создаёт свои данные. У разовой все материалы относятся
к одному конкретному исследованию.

## Что где хранить

| | Разовая задача | Регулярная задача |
|---|---|---|
| Пример | Почему просел `/blog/`, аудит микроразметки раздела | Ежемесячный отчёт, проверка новых страниц |
| Инструкция и инструменты | Задание, план и временный скрипт внутри папки задачи | Скилл в `skills/`, многоразовый скрипт в `tools/` |
| Входные данные | Нужные для сохранения исходники в папке задачи; человек может передать их через общий `temp/` | Исходники запуска в его папке; повторно используемые данные сайта в `inputs/`; новые материалы можно передать через `temp/` |
| Результат | В `tasks/<год>/<месяц>/<дата>-<название>/` | В `outputs/<задача>/<год>/<месяц>/run-<дата-запуска>/` для ежемесячной задачи |
| Что переиспользуем | Только явно выделенный и проверенный полезный фрагмент | Инструкцию, код, критерии и эталон; данные получаем заново |

## Рабочее пространство и сайты

Общие экспертные приоритеты хранятся в одном месте и действуют для всех сайтов.
Методики, скиллы и многоразовые инструменты также общие. Досье, параметры доступов,
разобранные входные данные и результаты относятся к выбранному сайту. Общая папка
`temp/` принимает материалы от человека до их разбора. Файл правил связывает
эти части: указывает общий файл приоритетов и пути к сведениям каждого сайта.

Пример рабочего пространства с несколькими сайтами:

```text
workspace/
├── AGENTS.md                 # или действующий файл правил агента; карта путей
├── PRIORITIES.md             # один общий файл экспертных установок
├── TASKS.md                  # список задач с указанием сайта
├── temp/                     # сюда человек просто кидает документы, скрины и другие входные
├── references/               # общие методики и эталоны
├── skills/                   # общие инструкции регулярных действий
├── tools/                    # общие многоразовые скрипты
└── sites/
    ├── alfa/
    │   ├── DOSSIER.md        # факты и источники alfa
    │   ├── ACCESS.md         # доступы и параметры источников alfa
    │   ├── inputs/           # входные alfa, используемые в нескольких задачах
    │   ├── outputs/
    │   │   └── traffic/2026/10/run-2026-11-08/
    │   │       ├── source.csv
    │   │       └── report.md
    │   └── tasks/
    │       └── 2026/11/2026-11-08-schema-audit/
    │           ├── input.csv
    │           ├── PLAN.md
    │           ├── check.py       # временный скрипт только этой задачи
    │           ├── report.md
    │           ├── fixes.csv
    │           └── manifest.json # при необходимости: список сохраняемого
    └── beta/
        ├── DOSSIER.md
        ├── ACCESS.md
        ├── inputs/
        ├── outputs/
        └── tasks/
```

В новых путях с датами используйте отдельные папки года (`YYYY`) и месяца (`MM`),
затем папку задачи или запуска с полной датой (`YYYY-MM-DD`). Для разовой задачи
год и месяц берутся из даты задачи. Для регулярного отчёта год и месяц относятся
к отчётному периоду. Например, результат за октябрь хранится в `2026/10/`,
даже если отчёт запустили 8 ноября.

Имена обозначают назначение файлов, а не комплект для установки. `skills/` —
принятое в пространстве место инструкций; путь зависит от существующей настройки.
Карту доступов можно хранить и общей таблицей с колонкой сайта.

**Один сайт с существующими файлами:** сначала найдите действующие правила,
приоритеты, досье и каталоги данных. Сохраните их пути. Если `DOSSIER.md`, `inputs/`,
`outputs/` и `tasks/` уже в корне, они там и остаются. Не создавайте `sites/alfa/`
или второй комплект файлов. Общие приоритеты могут уже находиться в доступном
документе за пределами папки сайта — достаточно указать путь к нему в правилах.

**Несколько сайтов с существующей структурой:** также не переносите всё под этот
образец. Например, общие `tasks/alfa/` и `outputs/alfa/` подходят вместо
`sites/alfa/tasks/` и `sites/alfa/outputs/`. Важно сохранять область действия:
общие установки в одном месте, сведения и результаты однозначно связаны с сайтом.
Не создавайте отдельные приоритеты для каждого сайта.

В этой практике `inputs/`, `tasks/` и `outputs/` без полного пути означают каталоги
**выбранного сайта**, а `skills/`, `tools/` и `references/` — общие каталоги
пространства. `temp/` — общая папка входящих материалов для всех сайтов.
Полные пути в примерах ниже соответствуют дереву выше.

## Temp: передать материалы агенту без сортировки

Человек кладёт документы, скриншоты, таблицы, выгрузки и другие файлы в общий
`temp/`, чтобы дать их агенту в контекст. Не нужно заранее выбирать сайт, папку
задачи или «правильное» место хранения и не нужно складывать файлы в корень.
Достаточно сказать: «Материалы для этой задачи в temp».

Агент разбирает материалы в рамках запроса:

1. Смотрит состав `temp/` и выбирает файлы, относящиеся к текущей задаче.
   Если непонятно, какие файлы использовать или к какому сайту они относятся,
   уточняет это; наличие файла в общей папке не делает его данными всех сайтов.
2. Читает нужные материалы. Если исходники должны сохраниться вместе с работой,
   копирует их в папку разовой задачи или регулярного запуска и указывает источник.
   Повторно используемые данные сайта можно разместить в его `inputs/`.
3. Результаты и собственные временные скрипты сохраняет в папке задачи или запуска.
   `temp/` остаётся местом передачи материалов от человека.
4. В конце сообщает, какие материалы использованы и где сохранены нужные копии.
   Очистка `temp/` — отдельное действие в разрешённых пользователем границах:
   перед удалением определяются конкретные файлы. Незнакомое, старое или уже
   прочитанное не считается автоматически ненужным.

`temp/` отличается от `inputs/`: первое — удобный вход без предварительной
сортировки, второе — уже отобранные данные конкретного сайта для повторного
использования. Для одного сайта используется тот же принцип. Если такое место
уже есть под другим именем, укажите его в правилах вместо создания второй папки.
`temp/` исключается из Git; это не запрет агенту читать переданные материалы.

## Как вести задачи

В существующем списке или общем `TASKS.md` различайте регулярные и разовые задачи.
Для нескольких сайтов указывайте сайт в каждой записи:

| Сайт | Тип | Задача | Когда | Инструкция / папка | Результат |
|---|---|---|---|---|---|
| alfa | Регулярная | Сводка трафика | После закрытия месяца | `skills/traffic-summary.md` | `sites/alfa/outputs/traffic/2026/10/run-2026-11-08/report.md` |
| alfa | Разовая | Аудит микроразметки | 2026-11-08 | `sites/alfa/tasks/2026/11/2026-11-08-schema-audit/` | `report.md`, `fixes.csv` в этой папке |

Для регулярной задачи зафиксируйте период, источники, параметры, формат результата,
способ запуска и проверки. Сбор и обработку данных с устойчивыми правилами
закрепляйте в коде: выгрузка, дедупликация, расчёты и проверки не должны каждый раз
изобретаться моделью. Модели оставляйте анализ и выводы. Если повторяется экспертная
работа, для которой нет фиксированного алгоритма, закрепите инструкцию и эталоны.

Повторы — повод пересмотреть процесс. Третий повтор в докладе служит сигналом
заметить регулярность; автоматический перевод каждой задачи в скрипт не нужен.
Полезный временный скрипт сначала проверьте на известном ответе, вынесите параметры
конкретного сайта и периода, затем перенесите в `tools/` и опишите вызов в скилле.
Старые результаты при этом остаются в папке исходной задачи.

Для разовой работы заранее определите итоговые файлы. В простой задаче достаточно
перечня в заметке; для большого набора можно использовать `manifest.json`, например
`{"keep": ["report.md", "fixes.csv", "input.csv"]}`. Сохраняйте также источники
и сведения о качестве, нужные для проверки. Сам список ничего не удаляет: перед
очисткой покажите конкретные кандидаты, не считайте все неупомянутые файлы мусором.

## Few-shot: инструкция и примеры

Few-shot дополняет инструкцию несколькими примерами нужного выполнения.
Его можно применять в промптах, скиллах, аналитике, редактуре, аудите, написании
кода и работе с инструментами. Особенно полезен там, где словами трудно точно
передать формат, стиль или критерий решения: примеры могут существенно улучшить
качество. Это не обязательное условие каждой задачи и не замена проверки результата.
Если короткой однозначной инструкции достаточно, не добавляйте примеры ради формы.

Показывайте вход и правильный выход. При типичной ошибке добавляйте явно
помеченное «как не надо» с объяснением. Отрицательный пример всегда сопровождайте
правильным, чтобы было понятно, какое действие ожидается вместо запрещённого.

Пример по приёму со [слайда 18](https://docs.google.com/presentation/d/19Km9pqSWkO8MYYQy6hK6UV9t7NFOYNlEDYHKxAOlIKQ/edit#slide=id.p18):
инструкция «убери лишние длинные тире» дополнена образцами редакторской правки.
Предложения ниже составлены для руководства, это не цитаты из доклада.

```text
Инструкция: убери тире, которыми заменено действие или связь между частями
предложения. Перестрой фразу, сохрани смысл. Не заменяй тире другим знаком
механически и не запрещай все тире независимо от контекста.

Пример 1
Вход: «Наша задача — проверить расчёты».
Как надо: «Мы проверим расчёты».
Как не надо: «Наша задача: проверить расчёты».
Почему: нужно выразить действие глаголом, а не заменить один знак другим.

Пример 2
Вход: «Источник недоступен — число заказов не проверено».
Как надо: «Число заказов не удалось проверить, потому что источник недоступен».
Как не надо: «Число заказов неверно».
Почему: отсутствие проверки не означает ошибку; при редактуре нельзя менять факт.

Теперь обработай новый текст по этому принципу: <текст пользователя>.
```

Другие применения со слайда 18:

| Задача | Чем дополнить инструкцию |
|---|---|
| Аудит микроразметки | Эталонами по типам страниц в `references/`, например `product.md` и `breadcrumbs.md`: вход, что проверяется, пример вывода |
| Скрипт или MCP | Рабочим примером похожего инструмента и ожидаемым результатом. При переносе с GSC на Метрику явно указать, какую логику сохранить и какие источники и параметры заменить |
| Нежелательные обещания | Как не надо: «Добавим разметку, и CTR вырастет». Как надо: «Разметка может дать право на расширенный результат; его показ и рост CTR не гарантированы». Пример со слайда показывает допустимую формулировку вместо одного запрета |

Для повторяющейся работы сохраняйте общие примеры в `references/` и ссылайтесь
на нужные из скилла. Короткие пары можно оставить прямо в инструкции. Примеры
одного сайта не становятся фактами другого: заменяйте данные параметрами или
обозначайте их как учебные. Большую подборку не копируйте во все скиллы.

## До выполнения: эталон, план и вопросы

Если задача уже выполнялась, возьмите один-два удачных результата. Выпишите из них
критерии в `references/`: нужные колонки, расчёты, структуру выводов. Для разных
типов страниц или задач лучше отдельные эталоны. Пример «было → стало» часто
точнее общего запрета.
Применяйте [few-shot](#few-shot-инструкция-и-примеры), когда пример помогает
объяснить требование; отсутствие эталона само по себе не блокирует работу.

Если эталона нет, соберите вводные и составьте план. В незнакомой области сначала
попросите объяснить, какие ограничения и вопросы вы могли упустить. Бриф дополняет
данные о сайте, источниках и результате, а не заменяет их.

```text
Составь план по этапам. Проверь его на серые зоны и развилки.
Сначала задай вопросы, ответы на которые меняют источники, расчёты и ограничения;
затем уточни формат. Для каждого допущения укажи последствия ошибки.
Запиши решения и оставшиеся неизвестные. У каждого этапа укажи вход, результат
и критерий готовности. Не начинай зависимую работу до ответа на критичный вопрос.
```

План готов к исполнению, когда определены источники, ограничения, этапы и критерии
приёмки. Для большой задачи храните его в папке задачи как `PLAN.md` с чекбоксами;
при необходимости вынесите подробности этапов в отдельные файлы. После этапа
запишите результат, путь к файлу, выполненные проверки и следующий шаг.

Для нового контекста подходит промпт: «Прочитай PLAN.md, решения и результаты
предыдущих этапов. Выполни первый невыполненный этап и отметь его после проверки».
Новая сессия полезна после длинного обсуждения; она не обязательна для каждой
небольшой задачи. Получатель этапа сначала проверяет наличие и формат входного
файла. Большую таблицу можно обрабатывать частями, сохраняя обработанные ID.

## При чём здесь Git

Дерево папок отвечает на вопрос «где искать работу», Git — «что хранить в истории
и передавать вместе с проектом». Инструкции, код и пригодные для общего хранения
эталоны отслеживаются; разовые материалы и итоги запусков исключаются.
Подробности и исключения — в [границах Git](git-boundaries.md).
Такая организация папок полезна и без Git.

## Когда практика нужна

- В корне смешаны материалы разных разовых работ.
- Повторяющаяся задача каждый раз начинается с восстановления инструкции.
- Формат результата меняется без причины, неизвестны нужный период или источник.
- После новой сессии приходится восстанавливать план и уже принятые решения.
- Работа переделывается из-за неуточнённых источников, методики или эталона.

Не переносите существующие папки без необходимости. Достаточно определить место
для следующей задачи и записать это в действующих правилах.
