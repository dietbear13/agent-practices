# Хранение ключей и безопасная проверка

Строковый API-ключ и JSON-файл сервисного аккаунта дают доступ к сервису.
Их значения не должны попадать в код, инструкции, досье, примеры, переписку
с агентом, отчёты или логи. JSON сам по себе не означает секрет: важны содержимое
и назначение файла. Публичный идентификатор проекта тоже не равен ключу доступа.

## Где хранить

Используйте принятое в проекте хранилище секретов или системное хранилище учётных
данных. Для CI и сервера передавайте секреты штатным механизмом среды запуска.
Разделяйте доступы разных сайтов и окружений; выдавайте только нужные права.

Для локальной работы допустим отдельный закрытый каталог с JSON-файлами
и локальный `.env` со строковыми ключами, если проект уже использует такой способ.
Ограничьте доступ средствами ОС владельцем и нужным процессом; проверьте наследуемые
права. Лучше держать JSON вне репозитория и общего каталога материалов агента.
Не помещайте секреты в общедоступную или автоматически публикуемую папку.
Для синхронизации и резервных копий нужен доступ, подходящий для секретов.
`.env` и JSON остаются обычными незашифрованными файлами: имя и скрытая папка
не защищают их от чтения. `.gitignore` тоже не ограничивает доступ.

Скрипт получает строку из переменной окружения, а путь к JSON — из отдельной
переменной. Сам JSON не нужно превращать в строковый ключ или вставлять в `.env`.
Загрузка `.env` должна быть предусмотрена приложением: файл не становится
окружением автоматически. Переменные окружения также нельзя печатать целиком.

В карте доступов указывайте сервис, сайт, окружение, права, владельца доступа,
название переменной или ссылку на запись хранилища. Значения ключей туда не нужны.
Пример без секретов и фрагмент правил есть в [образце](../examples/secrets.md).

## Как агенту найти проблемы

1. Определите границы проверки по запросу и рабочей папке. Прочитайте правила,
   карту доступов, `.gitignore` и места загрузки конфигурации. Не обследуйте
   домашнюю папку, глобальные настройки и внешние хранилища без основания в задаче.
2. Сначала проверяйте имена и метаданные. Найдите `.env`, возможные JSON-файлы
   учётных данных, приватные ключи и их копии в `temp/`, папках задач, выгрузках
   и архивах. Учитывайте скрытые и игнорируемые файлы. В Git сопоставьте их
   с `git ls-files`, `git status --short` и правилами игнорирования. Имя файла
   даёт кандидата на проверку, а не доказательство утечки.
3. Для поиска строк в коде, конфигурации, документах и логах используйте локальную
   проверку, которая возвращает только путь, номер строки и тип находки.
   Проверка должна искать и секретные поля JSON (`private_key`, `client_secret`,
   токены), и строковые ключи независимо от имени файла. Сначала убедитесь на
   искусственном примере, что инструмент скрывает значения, включая ошибки
   и отчёт. Не выводите совпавшие строки через обычный поиск, `cat`, `Get-Content`,
   diff или отладочный лог. Не отправляйте файлы во внешний сканер.
4. Не открывайте файл с секретами в контекст агента ради проверки. Если нужна
   проверка содержимого, выполните её локальным инструментом с ограниченным
   выводом. Если такого инструмента нет, сообщите о подозрительном пути и
   непроверенном содержимом; предложите владельцу проверить его локально.
   Не просите прислать ключ или полный JSON в чат.
5. Проверьте историю Git безопасным сканером с подавлением значений, если это
   входит в доступную область проверки. Не печатайте патчи истории. Если
   проверены только текущие файлы, явно укажите, что история не проверена.
   Без Git проверьте те же места хранения и копии, пропустив шаги про индекс.

Не запускайте найденный ключ для выяснения, действителен ли он. Поиск по шаблонам
может пропустить секрет или принять учебный пример за настоящий. Отделяйте
подтверждённую небезопасную настройку от подозрения и неизвестного. Отсутствие
находок не доказывает отсутствие утечек. Если инструмент всё же показал значение,
не повторяйте его в ответе и укажите, что оно могло попасть в журнал сессии.

## Как исправить находку

Для каждой проблемы покажите путь и безопасное описание, риск, целевое место
хранения, необходимые изменения и способ проверки. Например: «`tools/report.py`,
строка 18: встроенный ключ; заменить чтением `REPORT_API_KEY` из окружения».
Не показывайте исходную строку или часть ключа как доказательство.

- **Строка в коде или документе.** Настройте получение через выбранное хранилище
  или окружение, оставьте в шаблоне только пустое значение и описание переменной.
  Уберите значение из кода, заметок и примеров. Перенос выполняйте локально
  без вывода значения и без передачи его аргументом командной строки.
- **JSON среди материалов проекта.** Подготовьте закрытое место, перенесите файл
  без вывода содержимого, обновите путь у потребителей. Не перезаписывайте другой
  файл учётных данных. После проверки нового пути уберите лишние копии в рамках
  поручения; не удаляйте единственный рабочий экземпляр до проверки.
- **Секрет в отслеживаемом файле.** Добавьте точное правило игнорирования, проверьте
  его и отдельно исключите секретный файл из индекса с сохранением локального
  экземпляра. Для ключа внутри исходника замените значение в исходнике;
  исключать весь исходник не нужно. Игнорирование не очищает прошлые коммиты.
- **Ключ оказался в истории, общем логе, чате или опубликованном материале.**
  Сообщите о возможной компрометации. Владелец доступа должен отозвать или заменить
  ключ у поставщика и обновить потребителей; перенос файла не отменяет утечку.
  Если компрометация подтверждена, отзыв не откладывают ради удобства миграции.
  Не отзывайте доступы и не переписывайте общую историю Git без соответствующего
  поручения. Подготовьте конкретные действия и зависимости, чтобы не потерять
  рабочие интеграции. Очистку истории, копий и журналов разбирайте отдельно;
  она не заменяет отзыв ключа.

Если пользователь просит разбор, верните находки и правки для рассмотрения.
Если он уже поручил исправление, выполните разрешённую часть без повторного
согласования. Не меняйте глобальные права или доступы других проектов заодно.

## Как проверить результат

Проверьте, что потребитель получает строку или путь из предусмотренного источника,
а ошибка при отсутствии доступа не печатает секрет. Для разрешённого пробного
запуска используйте минимальный запрос без изменения данных и выводите только
статус. Не считайте перенос завершённым, пока рабочий потребитель не проверен;
если запуск недоступен, так и укажите.

Для локального файла проверьте права доступа, отсутствие лишних копий и
игнорирование по фактическому пути. При наличии Git проверьте также отсутствие
секретного файла в индексе и повторите безопасное сканирование изменённых файлов.
Не выводите обычный diff там, где удаляемая строка содержит ключ. Результат проверки
и сведения об отзыве фиксируйте без значений. Историю, резервные копии и внешние
публикации, которые не проверены, перечислите отдельно.

Рекомендации о жизненном цикле, ограничении доступа и исключении секретов из логов
опираются на [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet/).

## Когда практика нужна

- Ключи вставляют в скрипты, промпты, досье или настройки с общим доступом.
- JSON с доступами лежит рядом с выгрузками или попадает в Git.
- `.env` игнорируется, но ключ уже есть в истории или журнале.
- Непонятно, какой сайт и окружение используют конкретный доступ.
