# Границы Git

Эта практика дополняет [схему хранения задач](tasks.md). `.gitignore` не раскладывает
файлы по папкам и не мешает агенту читать старую выгрузку: он управляет тем,
какие неотслеживаемые файлы Git предлагает добавить в историю.

Отслеживайте то, что помогает повторять работу: скиллы, скрипты, правила,
приоритеты, эталоны, методики и досье, подходящие для хранения в этом репозитории по содержанию
и доступу. Код и документация самого проекта также остаются в Git.

Разовые задачи, выгрузки, временные файлы, результаты прогонов и секреты исключайте
через `.gitignore`. Выбирайте конкретные папки: правило для всех CSV может скрыть
нужные проекту справочники или тестовые данные.

## Пример

Общие инструкции лежат в `skills/`, скрипты в `tools/`, приоритеты в одном
`PRIORITIES.md`. В [основном примере структуры](tasks.md#рабочее-пространство-и-сайты)
данные расположены в `sites/<сайт>/`. Для него нужны правила `/sites/*/tasks/`,
`/sites/*/outputs/` и `/sites/*/inputs/`. Корневое `/tasks/` вложенные папки
не исключает. Для одного сайта с каталогами в корне подходят `/tasks/`,
`/outputs/` и `/inputs/`. [Фрагмент gitignore](../examples/gitignore.txt)
содержит оба варианта; оставьте подходящие правила для существующих путей.
Общий `temp/`, куда человек передаёт материалы без сортировки, исключается
правилом `/temp/` при любом числе сайтов. Игнорирование не мешает агенту читать
эти материалы по задаче и не означает, что их можно удалить.

В таблице ниже каталоги данных относятся к выбранному сайту; общие инструкции
и инструменты относятся ко всему рабочему пространству. Не исключайте `sites/`
целиком: вместе с выгрузками это скроет пригодные для Git досье и описания доступов.

| В истории Git | Вне истории Git |
|---|---|
| Инструкция регулярного отчёта и многоразовый скрипт | Выгрузки и итог каждого запуска в `outputs/` |
| Проверенный общий инструмент, выделенный из разовой работы | Вся папка разовой задачи `tasks/`, включая временные скрипты |
| Правила, подходящие для репозитория приоритеты, досье и `references/` | Закрытые входные данные `inputs/`, временные файлы и секреты |

Проверенный эталон можно сохранить в `references/` после удаления закрытых данных.
Это осознанно выбранный пример для будущих работ, а не все старые результаты.

Проверьте список отслеживаемых файлов (`git ls-files`) и статус (`git status`).
При необходимости `git check-ignore -v --no-index путь` покажет подходящее правило.
Игнорирование не убирает уже отслеживаемые файлы: их исключение из индекса нужно
разобрать отдельно, сохранив нужные локальные данные. Если секрет уже попал
в историю, одно правило игнорирования проблему не решает.
Порядок поиска строковых ключей и JSON-файлов, переноса и действий при раскрытии
описан в [практике хранения ключей](secrets.md).

`.gitignore` не заменяет резервное копирование. Для важных результатов и закрытых
досье определите отдельное место хранения с подходящим доступом и резервной копией.
Если выгрузки накапливаются, можно определить сроки хранения отдельно для исходных
данных и итоговых отчётов. Например, исходные выгрузки можно хранить до завершения
сверки, если их легко получить снова, а отчёты — пока они нужны для сравнения периодов.

Секреты не должны попадать также в промпты, отчёты и логи. Скрипт получает ключ
из предусмотренного проектом хранилища; агенту достаточно названия переменной.
`.gitignore` не ограничивает чтение файлов агентом. Если нужна такая защита,
она задаётся поддерживаемыми клиентом правами доступа; менять настройки ради
чтения этого руководства не требуется.

## Когда практика нужна

- Выгрузки и временные результаты попадают в изменения вместе с кодом.
- Непонятно, какие файлы должны получать другие участники проекта.
- Ценные материалы существуют только в локальной игнорируемой папке.
